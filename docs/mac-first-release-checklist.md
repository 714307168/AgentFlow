# mac 首发发布检查清单

更新时间：2026-04-19

这份清单用于 `R-mac-first` 节点，目标是把 mac 首个可安装版本从“能打包”推进到“可签名、可更新、可回滚、可验证”。

## 1. 发布目标

首发必须至少满足：

- 有可安装产物
- 有明确的架构策略
- 有签名和 notarization 路径
- 有更新中心接入方案
- 有日志目录和数据目录约定
- 有失败回滚方式

## 2. 产物与架构

发布前明确：

- 是只发 `arm64`，还是发 `universal`
- 文件名约定是什么
- 更新中心 `platform` 字段如何命名
- 是否和 Windows 共用同一个桌面版本号

建议首发优先级：

1. 优先 `arm64`
2. 如果构建和体积可接受，再评估 `universal`
3. 不建议首发同时维护多套安装包命名规则

## 3. 构建检查

发布前至少确认：

- Electron 主进程能正常启动
- renderer 资源完整
- 本地 CLI 探测逻辑在 mac 上可执行
- 应用图标、包名、版本号、产物名一致
- 构建脚本不会依赖 Windows-only 路径或命令

建议记录：

- 构建命令
- 构建机架构
- 产物路径
- 产物 SHA256

## 4. 签名与 Notarization

首发前明确这几个问题：

- 是否使用 `Developer ID Application`
- 是否已经接入 notarization
- 公证完成后是否执行 staple
- 用户侧首次打开是否还会出现 Gatekeeper 拦截

至少核对：

- 签名证书名称
- notarization 提交方式
- notarization 成功记录
- staple 后最终产物哈希

如果这一轮还做不到自动化 notarization，也要至少把手动流程写清楚，不要让首发依赖临时记忆。

## 5. 更新中心接入

接入前确认：

- 更新中心是否新增 mac 对应的 `platform` 值
- `arch` 字段是否区分 `arm64 / universal`
- 更新检查接口是否能正确返回 mac 版本
- 下载附件、文件名、SHA256 是否与更新中心记录一致

首发至少要做一次：

1. 本地版本低于服务端版本
2. `/api/update/check` 返回新版本
3. 客户端能正确展示更新信息
4. 客户端能下载到正确的安装包

## 6. 日志与数据目录

首发前写清楚：

- 应用配置目录
- 运行日志目录
- 诊断导出目录
- 下载缓存目录
- 自动更新缓存目录

同时确认：

- 路径对普通用户可写
- 路径不会误落到仓库目录或临时目录
- 日志上传和诊断导出在 mac 上不依赖 Windows 专有命令

## 7. 权限与系统行为

首发必须核对这些系统行为：

- 应用首次启动
- Dock / 窗口唤起
- 打开日志目录
- 打开本地数据目录
- 外部链接打开
- 文件下载后打开安装包
- 应用退出并进入更新安装流程

如果有通知、托盘、自动启动、文件访问权限等系统特性，也要明确首发是否支持。

## 8. 回滚策略

首发前必须先准备回滚，不要等出问题后再补。

至少明确：

- 更新中心是否能撤回已发布版本
- 是否保留上一个稳定构建
- 如果 notarization 或下载包异常，用户如何回退
- 是否需要在文档中保留“手动下载稳定版”入口

## 9. 最小验收清单

上线前最少跑一遍：

- 安装
- 登录
- relay 连接
- 项目列表同步
- 聊天与消息刷新
- 附件/文件消息展示
- 设置页核心入口
- 更新检查
- 日志与诊断导出
- 卸载后重装或覆盖安装

## 10. 发布记录模板

推荐记录：

```text
R-mac-first
version:
platform:
arch:
artifact:
sha256:
notarization:
update center release id:
github release tag:
verified by:
notes:
```

## 11. 当前结论

`mac` 首发不应只是“把 Electron 打出一个包”，而应把构建、签名、公证、更新、日志和回滚一起闭环。后续一旦开始做 `R-mac-first`，先按这份清单过一遍。
