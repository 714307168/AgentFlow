# 平台首发后边界推进回写示例

更新时间：2026-04-21

这份文档不再讲完整模板，而是直接给出“平台首发后，路线图里该怎么回写继续扩边界或延后扩边界”的短样例。

它适合解决这几个问题：

- 平台已经首发，但路线图里不知道该怎么简短说明后续是继续扩范围还是先稳住
- 已经有首发摘要和首发后观察摘要，但缺少更接近真实路线图语气的短句样例
- 想把 `mac / iOS / 小程序` 这类平台后续推进节点继续控制在摘要级别，不回到长段过程说明

建议配合：

- [平台首发摘要模板](./platform-first-release-summary-template.md)
- [平台首发后观察摘要模板](./platform-first-post-release-observation-template.md)
- [平台专项路线图回写示例](./platform-track-roadmap-writeback-examples.md)

## 1. 使用方式

推荐顺序：

1. 先在首发摘要或首发后观察摘要里保留完整边界、风险和结论。
2. 再从完整内容里抽 2 到 4 行回写到路线图。
3. 路线图里只保留“当前边界是否维持、是否扩边界、下一步动作”，不要重新写成长段观察过程。

路线图里最好让人一眼看出：

- 当前是继续稳首发，还是已经开始扩边界
- 扩的是哪类能力
- 哪些范围仍然明确延后
- 下一步是继续验收、继续观察，还是准备下一轮发版

## 2. 继续扩边界示例

### 2.1 mac

~~~text
- R-mac-first 首发后开始扩边界：
  - 首轮观察完成后，继续补签名自动化、更新安装体验和通用包能力
  - 当前扩的是首发后桌面可维护性，不是重新扩大产品定位
  - 下一步按增量能力继续验收和分批发版
~~~

### 2.2 iOS Safe Track

~~~text
- R-ios-safe-track 首发后继续小步扩边界：
  - 在保持 Safe Track 定位不变的前提下，补文件接收稳定性和弱网恢复体验
  - 暂不扩成完整远控终端，也不追求安卓同等覆盖
  - 下一步继续按轻量能力补验收和观察
~~~

### 2.3 小程序 Lite

~~~text
- R-mini-lite 首发后继续补轻入口边界：
  - 当前继续优化状态刷新、快速回复和重连反馈
  - 只做 Lite 体验打磨，不扩成完整移动端
  - 下一步跟随轻量验收结果决定是否继续补交互细节
~~~

## 3. 延后扩边界示例

### 3.1 mac

~~~text
- R-mac-first 首发后暂缓扩边界：
  - 当前先维持可安装、可启动、可同步和可更新的首发范围
  - 签名、公证和安装链路仍优先于新增桌面能力
  - 下一步继续稳首发质量，扩边界延后到下一轮
~~~

### 3.2 iOS Safe Track

~~~text
- R-ios-safe-track 首发后继续维持窄边界：
  - 当前先稳登录、项目列表、消息查看和轻量回复
  - 审核约束、后台限制和弱网恢复仍未支撑更大范围扩展
  - 下一步先完成观察收口，再决定是否追加能力
~~~

### 3.3 小程序 Lite

~~~text
- R-mini-lite 首发后延后扩边界：
  - 当前继续保持查看、快速回复和状态确认的轻入口定位
  - 不引入重设置、大缓存和完整实时控制能力
  - 下一步先稳住 Lite 体验，再考虑是否有必要补更深能力
~~~

## 4. 不推荐写法

不要在路线图里继续写这种又长又虚的段落：

~~~text
首发后整体情况还可以，后面会根据观察结果继续调整平台能力范围，之后再看是继续做体验优化，
还是扩大能力，或者先不动，具体等后续情况再定。
~~~

原因：

- 看不出到底是继续扩边界还是延后扩边界
- 看不出当前优先稳的是哪些范围
- 看不出下一步动作是验收、观察还是下一轮发版
- 很容易把路线图重新写回状态汇报

## 5. 当前结论

后续平台首发后的边界推进回写时，优先复用这份文档里的短样例，先把完整观察结论压成路线图语气，再决定是否需要补更详细的专项文档。
