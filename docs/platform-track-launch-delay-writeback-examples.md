# 平台专项首发延期后的短回写示例

更新时间：2026-04-22

这份文档不再讲完整模板，而是直接给出“平台专项原本准备首发，但因为链路、审核、依赖或风险问题需要延期时，路线图里该怎么回写”的短样例。
它适合解决这几个问题：

- 平台专项经常在接近首发时被迫延期，但路线图里缺少明确的“首发延期”语气
- 已经有暂停、收窄边界和风险回写样例，但缺少专门描述“延期首发、不等于整体暂停”的写法
- 想把 mac / iOS / 小程序 这类平台节点延期的原因、当前保留范围和新的首发前动作稳定控制在摘要级别

建议配合：
- [平台专项重新收窄边界后的短回写示例](./platform-track-rescope-writeback-examples.md)
- [平台专项阶段暂停与延后推进回写示例](./platform-track-pause-writeback-examples.md)
- [平台首发后风险与热修回写示例](./platform-first-risk-writeback-examples.md)

## 1. 使用方式

推荐顺序：
1. 先在平台专项文档、首发清单或风险文档里写清楚为什么延期、当前保留哪些范围、延期后先做什么。
2. 再从完整内容里抽 2 到 4 行回写到路线图。
3. 路线图里只保留“为什么延期、当前边界怎么处理、首发前还要补什么、何时再判断能否发”，不要把延期过程写成长段说明。

路线图里最好让人一眼看出：

- 这是首发延期，不是整条专项都停掉
- 当前首发范围是否继续有效，还是已经收窄
- 延期后先补的是链路、审核、依赖还是验收
- 下一次判断是否可发的前提条件是什么

## 2. 因首发链路不稳延期

### 2.1 mac

~~~text
- R-mac-first 当前首发延期：
  - 签名、安装或更新链路还没压实，当前不直接进入首发发版
  - 首发边界继续保留在构建、签名、安装和更新主链路，不并回更大桌面范围
  - 下一步先补链路验收，确认可安装可更新后再重新判断首发时间
~~~

### 2.2 iOS Safe Track

~~~text
- R-ios-safe-track 当前首发延期：
  - Safe Track 首发前主链路和弱网恢复信号还不够稳定，暂不进入对外首发
  - 当前继续维持登录、项目列表、消息查看和轻量回复边界，不扩到完整远控能力
  - 下一步先补主链路验证和审核前检查，再决定新的首发窗口
~~~

## 3. 因审核或依赖问题延期

### 3.1 iOS Safe Track

~~~text
- R-ios-safe-track 当前首发延期：
  - 审核约束和后台限制问题尚未完全收口，当前先延后首发
  - Safe Track 窄边界继续有效，但不在本轮继续扩展更深端侧交互
  - 下一步先压审核相关问题和弱网恢复，再重新评估首发条件
~~~

### 3.2 小程序 Lite

~~~text
- R-mini-lite 当前首发延期：
  - 轻入口依赖的交互细节和验收入口还没完全对齐，当前先不首发
  - Lite 定位保持不变，只保留查看、快回和状态确认主链路
  - 下一步先补轻量验收和交互核查，再决定新的首发节奏
~~~

## 4. 因风险控制主动延期

### 4.1 mac

~~~text
- R-mac-first 当前主动延期首发：
  - 为避免把不稳定的更新链路直接带到首发版本，当前先延后发布时间
  - 首发范围继续收窄到最小可发布主链路，不把体验增强并回本轮
  - 下一步先完成风险收口和回退验证，再重新推进首发
~~~

### 4.2 小程序 Lite

~~~text
- R-mini-lite 当前主动延期首发：
  - 当前先保留轻入口最小可用链路，不把仍有风险的交互细节带进首发
  - Lite 范围继续维持，不额外扩边界或提升产品定位
  - 下一步先压轻入口稳定性和验收反馈，再决定首发时间
~~~

## 5. 延期但不退出专项推进

### 5.1 iOS Safe Track

~~~text
- R-ios-safe-track 当前首发延期但继续推进：
  - 虽然延期，但专项不转暂停，继续只围绕首发前主链路和审核问题收口
  - 当前不把延后范围自动并回，也不改 Safe Track 轻量定位
  - 下一步先做首发前核查和验收复测，再决定是否恢复发版计划
~~~

### 5.2 mac

~~~text
- R-mac-first 当前首发延期但继续推进：
  - 延期只影响发布时间，不影响当前围绕安装、更新和回退链路的专项收口
  - 桌面更大范围体验优化继续延后，不并入首发前阶段
  - 下一步先稳住首发主链路，再重新排首发窗口
~~~

## 6. 不推荐写法

不要在路线图里继续写这种又长又模糊的段落：

~~~text
这个平台原本准备发了，但现在还有一些问题，所以后面首发时间可能要往后放，具体什么时候发、现在先做哪些、哪些范围是不是还保留，之后再看情况安排。
~~~

原因：

- 看不出这是首发延期还是整个专项暂停
- 看不出当前首发边界是否还有效
- 看不出延期后先补什么
- 看不出何时再判断能不能发

## 7. 当前结论

后续平台专项如果不是取消首发，而是把首发延后，优先复用这份文档里的短样例，把延期原因、保留范围和首发前动作压成路线图语气，避免总览继续膨胀。
