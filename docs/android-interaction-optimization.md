# Android 交互设计优化方案

## 目标

这份文档用于统一 Android 端后续交互优化方向，重点解决以下问题：

- 信息层级不稳定，状态变化容易干扰主操作
- 页面密度不一致，部分区域占空间过大
- 聊天、活动、队列、代理之间的导航心智不够统一
- 实时同步场景下，用户对“发生了什么”感知不够稳定
- 弱性能设备上，频繁刷新和大列表渲染容易放大卡顿感

优化目标不是单纯“更好看”，而是让 Android 端更接近一个稳定、可长期使用的工作终端。

## 当前信息架构

现有底部导航分为三类：

- `消息`
- `代理`
- `设置`

现有主要页面：

- 消息列表页：项目会话入口
- 代理页：项目分组、协作组、加入群组入口
- 聊天页：会话、活动、队列三种视图切换
- 协作组聊天页
- 设置页

这套结构本身没有问题，问题主要出在状态呈现方式和页面节奏。

## 现状问题

### 1. 首页和列表页缺少明确主次

- 标题、连接状态、按钮、更新提示、列表都在抢注意力
- 用户真正最常点的是“进入会话”，但视觉焦点经常被状态条和说明卡片抢走

### 2. 实时状态与内容混在一起

- 运行中、排队中、已就绪、在线/离线等状态很重要
- 但这些状态不应该持续大面积占据聊天空间
- 状态应该“可感知”，但不能“压住内容”

### 3. 聊天页缺少稳定的操作节奏

- 顶部信息较多，容易显得厚重
- 会话/活动/队列切换后，用户对当前所在视图的感知不够强
- 输入区视觉重量偏高，容易把消息内容压缩得太厉害

### 4. 列表反馈不够“微信式”

- 用户预期是：列表稳定、最新会话靠前、状态轻提示、内容是主角
- 当前更偏“工程调试界面”，而不是“长期沟通界面”

### 5. 同步和刷新感知不够自然

- 用户更关心“我发的消息有没有到”“对方有没有开始处理”“有没有完成”
- 不关心每一次底层同步细节
- 因此刷新动画、状态变化、排序变化必须更克制

## 设计原则

### 1. 内容优先

- 会话文本、最新消息、关键活动优先展示
- 状态、按钮、统计、更新提示都应该退到次级层

### 2. 状态弱打扰

- 在线、运行中、排队中必须可见
- 但只用小徽标、轻色块、窄通知条表达
- 避免大块状态卡片长期占位

### 3. 结构稳定

- 列表排序稳定
- 页面切换位置稳定
- 同类元素尺寸和留白稳定
- 避免一有实时事件整个界面明显跳动

### 4. 操作单路径

- 用户在任意页面都应清楚：
- 我现在在哪
- 我接下来点哪里
- 点了以后会发生什么

### 5. 低性能优先

- 默认只渲染必要内容
- 降低大面积渐变、频繁重组、复杂动画使用频率
- 让“稳定”和“快”优先于“花”

## 交互优化方向

## 一、底部导航

### 当前问题

- 已经有基础分栏，但仍偏“容器感”
- 用户对“消息”和“代理”的职责区别还不够强

### 优化方向

- 保持三栏不变：`消息 / 代理 / 设置`
- `消息` 只看最新会话，不做复杂分组
- `代理` 承担完整通讯录能力：
  - 项目分组
  - 远程分组
  - 协作组
  - 外部设备
- `设置` 保持系统配置入口，不混业务入口

### 设计要求

- 底部导航固定、轻量、悬浮感
- 标签字数保持 2 到 3 个字
- 选中态只强化当前项，不扩大按钮尺寸

## 二、消息列表页

### 页面职责

消息页应该只解决两个问题：

- 最近谁有新动态
- 我点进去继续聊谁

### 推荐结构

1. 顶部轻量状态栏
- 页面标题
- 连接状态
- 刷新按钮
- 不再放大量描述性说明

2. 轻量摘要条
- 项目总数
- 运行中数量
- 排队数量
- 离线数量

3. 会话列表
- 最新消息在最上面
- 每行只保留：
  - 项目名
  - 最新摘要
  - 状态徽标
  - 时间
  - 未读或运行提示

### 不建议继续保留的做法

- 大面积空白头图
- 多段说明文字
- 频繁跳动的排序
- 状态变化导致整卡重排

## 三、代理页

### 页面职责

代理页是“通讯录”，不是第二个消息页。

它负责：

- 找项目
- 找远程设备
- 找协作组
- 加入协作组

### 推荐结构

1. 顶部状态栏
- 标题
- 连接状态
- 刷新/重连

2. 概览条
- 项目数
- 协作组数
- 可选的在线设备数

3. 主体列表
- 默认分组
- 自定义分组
- 远程分组
- 协作组分组

### 关键交互

- 分组支持折叠
- 排序稳定
- 中文按拼音首字母排序
- 每一项只保留最关键的元信息

### 视觉要求

- 项目卡片与协作组卡片保持同一设计语言
- 在线状态只用小圆点或小徽标表达
- 不使用重色大卡片堆叠

## 四、聊天页

聊天页是 Android 端最核心页面，后续优化优先级最高。

### 1. 头部

推荐保留：

- 返回
- 项目名
- 当前会话名
- 连接状态
- 运行状态
- 会话切换
- 模型切换

推荐弱化：

- 冗长说明
- 过多副标题
- 大块背景

头部应该像“工作中的聊天窗口”，而不是“管理面板”。

### 2. 视图切换

当前三类视图保留：

- 会话
- 活动
- 队列

优化原则：

- 三个标签宽度一致
- 文案尽量短
- 计数放在标签内
- 切换后默认定位到最新内容
- 上滑加载历史必须只影响当前视图

### 3. 运行状态条

运行中、排队中、离线时仍然需要提示，但建议改成：

- 默认单行摘要
- 可展开查看详情
- 靠近标签区，而不是压在消息流中间
- 只有状态变化明显时才强调颜色

### 4. 消息区

消息区要坚持“聊天内容第一”：

- 文本气泡优先
- thinking、activity、cli 走差异化但克制的样式
- 图片预览直接可看
- 文件卡片紧凑
- 时间信息不要抢主文案

### 5. 输入区

输入区建议长期保持稳定：

- 左侧附件
- 中间输入框
- 右侧发送
- 运行中时增加停止按钮

附件托盘原则：

- 仅在有附件时出现
- 可横向滚动
- 单个附件卡片紧凑
- 删除按钮必须明确、统一，不允许乱码或临时字符

## 五、协作组页面

### 页面定位

协作组不是“任务流水”，而是多人工作聊天群。

因此交互要更像群聊：

- 成员清晰
- 消息主导
- @ 提示明确
- 状态提示收敛

### 优化方向

- 头部显示群名、成员数、运行状态摘要
- 群消息与私聊消息视觉明确区分
- 输入框的 @ 建议用候选面板，而不是纯手输
- 系统消息和业务消息视觉分层

## 六、状态反馈体系

Android 端所有反馈建议统一成四级：

### 1. 静态状态

- 在线
- 离线
- 已就绪
- 运行中
- 排队中

适合用：

- 小徽标
- 小色块
- 简短文案

### 2. 过程反馈

- 正在同步
- 正在发送
- 正在下载
- 正在加载更多

适合用：

- 小 loading
- 顶部轻提示
- 列表内局部 loading

### 3. 成功反馈

- 已发送
- 已完成
- 已下载
- 已更新

适合用：

- Toast
- Snackbar
- 小型完成提示

### 4. 错误反馈

- 发送失败
- 连接中断
- 下载失败
- 权限不足

适合用：

- 底部 Snackbar
- 重试按钮
- 尽量附带下一步动作

## 七、动画与动效

动效应该服务于“稳定感”。

建议保留：

- 页面进入淡入
- 列表轻微位移出现
- 运行状态条展开/收起
- 新消息到达时轻微滚动

建议减少：

- 大面积渐变动画
- 高频闪烁
- 状态变化导致整页重排动画
- 列表项频繁重新测量

## 八、性能感知优化

虽然这是交互文档，但 Android 端体验问题很多其实是性能问题伪装出来的。

### 交互上要配合的性能策略

- 消息页默认只看最近会话
- 聊天页默认只渲染最近一屏到两屏消息
- 活动和队列只显示最近一段
- 历史消息按需分页加载
- 页面切后台再回来时只补必要同步
- 列表 key 必须稳定
- 排序依据必须稳定，不允许因心跳和状态流频繁波动

## 九、视觉语言建议

Android 端后续视觉建议统一成以下方向：

- 轻卡片
- 中等圆角
- 浅对比背景
- 重点色只用于动作和状态
- 文字信息密度高于装饰密度

建议避免：

- 过深阴影
- 大块高饱和背景
- 说明文字过多
- 一页出现太多不同风格的卡片

## 十、实施优先级

### P0

- 消息页结构稳定化
- 代理页通讯录化
- 聊天页头部和输入区压缩
- 状态反馈统一
- 历史加载与默认定位逻辑统一

### P1

- 协作组聊天体验优化
- 运行状态条标准化
- 列表搜索体验优化
- 发送/同步/完成反馈统一

### P2

- 更完整的动效系统
- 主题细节打磨
- 平板/大屏自适应
- 安卓语音输入和多模态入口融合

## 推荐落地顺序

建议按下面顺序开发，而不是同时改很多页面：

1. 消息页
2. 聊天页
3. 代理页
4. 协作组页
5. 设置页细节统一

原因很简单：

- 用户高频操作主要集中在消息和聊天
- 这两页做好，整体体验会立刻明显提升
- 代理页和协作组页再补上，系统才完整

## 验收标准

交互优化完成后，至少应满足以下标准：

- 用户首次打开时，能在 3 秒内理解当前信息架构
- 用户能在 1 次点击内进入最近会话
- 聊天页不会被状态信息长期压住
- 状态变化不会引起列表明显乱跳
- 弱性能设备上，页面切换和滚动不再出现明显掉帧感
- 群聊、私聊、代理列表的角色边界清楚

## 下一步建议

基于这份文档，下一轮开发建议拆成三个独立任务：

1. 安卓消息页和聊天页交互重构
2. 安卓代理页通讯录化与协作组入口收敛
3. 安卓状态反馈与分页加载统一

这样改造成本更可控，也更容易逐轮验收。
