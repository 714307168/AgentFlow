# 跨端文件传输协议与回执验收清单

更新时间：2026-04-19

这份文档用于把当前“图片和文件并入消息时间线”的能力收口成一个可以跨端复用的统一协议约束，并给 `R-cross-end-transfer` 提供一份可以直接执行的验收清单。

它不替代现有消息同步主链路，而是明确：

- 文件传输仍然是消息时间线的一部分
- 传输状态要通过统一回执对齐
- 新端接入时优先复用同一套 transfer 生命周期，而不是各做一套上传下载逻辑

## 1. 目标与边界

当前统一目标：

- 发送图片或文件时，先落消息，再挂传输元信息
- 上传、下载、回执、失败重试都围绕同一个 `transfer_id`
- 不额外再做独立“文件中心会话协议”
- 不破坏现有 `revision / meta / delta / after_seq` 的同步主线

当前不在这份协议里扩展的内容：

- 音视频流式传输
- 超大文件分片秒传优化
- 脱离消息时间线单独存在的网盘式文件空间

## 2. 统一对象模型

每条文件消息至少应能追踪这些字段：

- `project_id`
- `message_id`
- `transfer_id`
- `sender_device_id`
- `filename`
- `size`
- `mime_type`
- `content_digest`
- `storage_key`
- `status`
- `failure_code`
- `created_at`
- `updated_at`

说明：

- `content_digest` 用于内容去重、下载校验和跨端缓存命中，不要求和项目级 `project_signature` 复用同一算法，但字段职责必须清晰区分。
- `storage_key` 只描述 relay-server 存储定位，不应直接暴露底层真实文件路径。
- `status` 只保留一套跨端统一枚举，避免桌面端、Android、后续 iOS 各自发明状态名。

## 3. 统一状态机

推荐收口为以下主状态：

1. `created`
2. `uploading`
3. `uploaded`
4. `delivered`
5. `opened`
6. `failed`
7. `expired`
8. `cancelled`

状态含义：

- `created`：消息已经创建，但文件还未开始上传或服务端未确认接管。
- `uploading`：发送端正在上传，允许显示进度，但不要把半成品当成可下载文件。
- `uploaded`：relay-server 已经持有完整文件，可供接收端下载。
- `delivered`：目标端至少有一个授权接收方已经成功拿到文件并完成完整性校验。
- `opened`：接收方已经实际打开、保存或预览文件。
- `failed`：上传、下载、校验或授权任何一环明确失败。
- `expired`：文件被服务端回收、过期或已不可再下载。
- `cancelled`：发送侧主动取消，不再继续传输。

## 4. 回执语义

统一只认三类对用户可见的回执结果：

- `uploaded`
- `delivered`
- `opened`

失败则通过 `failed` 搭配 `failure_code` 表达。

推荐失败码最少覆盖：

- `upload_failed`
- `download_failed`
- `digest_mismatch`
- `not_authorized`
- `not_found`
- `expired`
- `storage_unavailable`
- `user_cancelled`

约束：

- 不要把“客户端本地开始下载”误报成 `delivered`。
- 不要把“下载完成但未校验 digest”误报成 `delivered`。
- `opened` 是增强回执，不应阻塞消息主链路。

## 5. 标准流转

### 5.1 发送端

1. 创建一条文件消息，拿到 `message_id` 和 `transfer_id`。
2. 本地记录 `created`，并把消息立即插入时间线。
3. 上传文件到 relay-server。
4. 服务端确认文件可用后，将状态推进到 `uploaded`。
5. 如上传失败，转为 `failed` 并带 `failure_code`。

### 5.2 服务端

1. 负责接收文件、保存元信息、生成可下载定位。
2. 把文件状态并入项目消息同步结果，而不是单独开一套独立同步入口。
3. 只向有项目权限的设备暴露可见文件消息和下载信息。
4. 对下载成功、打开成功、失败重试等回执做幂等收口。

### 5.3 接收端

1. 通过正常消息同步先拿到文件消息壳和传输元信息。
2. 有需要时再按需下载文件内容，避免列表阶段就抢流量。
3. 下载完成后先做 `content_digest` 校验，再上报 `delivered`。
4. 用户实际打开、预览或保存后，再上报 `opened`。

## 6. 与省流量策略的关系

文件传输协议必须继续服从当前省流量策略：

- 列表同步优先返回消息壳、状态和必要元信息，不主动回传大文件内容。
- 文件消息继续走消息时间线增量同步，不单独参与高频全量比对。
- 冷项目不因为存在历史附件就频繁回刷文件状态。
- 本地已有同 `content_digest` 文件时，可优先命中缓存并跳过重复下载。
- 项目级 `project_signature` 只用于判断项目消息面是否有变化，不替代文件内容校验。
- HTTP 返回继续允许 gzip 压缩，但文件二进制本体不做二次无意义压缩。

## 7. 跨端能力降级原则

各端能力允许不同，但协议不应分叉。

当前建议：

- desktop-win：支持发送、下载、打开、回执、失败重试
- Android：支持发送图片和文件、下载、打开、回执
- iOS Safe Track：首发至少支持接收、下载、打开、基础回执
- 微信小程序 Lite：首发只承担查看文件消息、下载、有限预览，不承担重型上传

降级要求：

- 不支持的端要明确展示“当前端不支持此操作”，不要静默失败。
- 不支持 `opened` 回执的端可以只上报 `delivered`，但不能伪造 `opened`。

## 8. 验收清单

### 8.1 通用验收

- [ ] 文件消息能直接进入项目消息时间线
- [ ] 文件消息在列表、详情、历史恢复后 ID 保持稳定
- [ ] 上传失败时能落明确失败态和失败原因
- [ ] 下载完成后只有在 digest 校验通过时才写入 `delivered`
- [ ] 打开文件后能正确写入 `opened`
- [ ] 同一回执重复提交不会造成状态乱跳
- [ ] 无项目权限的设备看不到该文件消息和下载入口
- [ ] 冷项目同步不会因为历史文件导致频繁全量回刷

### 8.2 desktop-win

- [ ] 发送图片和普通文件都走同一套消息入口
- [ ] 文件消息发送后仍可继续聊天，不阻塞主输入流
- [ ] 下载目录、打开动作、失败重试可追踪

### 8.3 Android

- [ ] 从消息流里直接发送图片和文件，不额外跳独立功能入口
- [ ] 进入聊天页后文件消息位置正确，不因历史回填跳动
- [ ] 下载、安装器打开、分享或外部预览行为能正确回执

### 8.4 iOS Safe Track

- [ ] 至少完成接收、下载、打开、基础回执闭环
- [ ] 不支持的重型上传能力已明确标注边界

### 8.5 微信小程序 Lite

- [ ] 文件消息可见
- [ ] 支持轻量下载或跳转下载
- [ ] 不承担后台长任务上传

## 10. 当前结论

后续所有文件与图片能力，优先都按“消息时间线 + 统一 transfer 生命周期 + 统一回执”推进。这样新端接入时只是在能力层做增减，而不是重新发明一套传输协议。
