# 蜂群任务空间设计

> 状态：实施中。本文定义 AgentFlow 现有协作组强制迁移后的产品和安全边界；它不把“加入群”视为自动获得代码或文件写入权。

## 1. 目标

将协作组升级为蜂群任务空间（Swarm Workspace）：人类与多个本地或远程 Agent 围绕一个目标协作，PM 负责拆解与协调，成员按依赖并行执行，用户可在运行中调整、追加和验收。

单项目仍是默认的轻量入口。它在领域模型中等价于只有一个执行成员的蜂群，但不要求用户创建协作组，也不改变原有项目会话、队列或停止语义。

## 2. 用户模型

```
Swarm Workspace
├─ 人类参与者：提出目标、补充上下文、批准/驳回
├─ PM Agent：生成和维护任务图，不直接取得额外文件权限
├─ 执行 Agent：绑定一个项目运行时（账号、Provider、模型、工作区）
├─ 审阅/测试 Agent：默认只读或在隔离工作区执行
└─ 任务图：任务、依赖、负责人、状态、产物和验收记录
```

一个 Agent 成员不是裸模型名，而是已授权的运行配置：`账号 + Agent 设备 + 项目 + Provider + Model + 权限范围`。当前 Provider 为 Claude 和 Codex；后续 Provider 必须通过同一运行时适配器接入，不能仅把模型名称写入配置。

## 3. 核心原则

1. **显式授权**：加入群只获得协作会话访问权。群主批准并绑定具体 Agent/项目后，才能成为执行成员。
2. **最小文件权限**：成员仅能访问其绑定项目及 `allowedPaths`；PM 不能因编排身份获得额外权限。
3. **单写入者**：同一工作区同一时刻最多一个 `write` 成员。并行编码必须使用不同 worktree/分支；审阅、规划和测试默认不写主工作区。
4. **任务图优先**：群消息是交互入口，任务、依赖、产物、验收和失败原因是状态真相。
5. **多账号隔离**：账号不共享 API Key、Provider 登录态或本地文件。跨账号成员通过 Relay 传递最小任务上下文与结果。
6. **可撤销**：移除成员、离开或被踢时，立即停止未开始调度并撤销由蜂群授予的访问；正在执行的远端任务进入可审计的取消/超时流程。

## 4. 数据与同步边界

| 数据 | 位置 | 说明 |
| --- | --- | --- |
| 蜂群定义、成员绑定、任务图、调度策略 | 宿主桌面 | 当前桌面是任务真相来源，支持本地恢复。 |
| 对话、流式结果、验收记录 | 宿主桌面 SQLite | Relay 只转发，不保存完整工作内容。 |
| 群号、账号成员关系、可撤销访问授权 | Relay | 仅保存发现、成员资格和受控访问所需元数据。 |
| 模型密钥、CLI 登录态、实际工作区 | 各 Agent 所在设备 | 永不通过 Relay 或群快照复制。 |

Android 是控制和观察端：可看任务图、发送指令、批准/驳回和查看产物摘要；不能绕过宿主授权直接访问其他账号的文件。

## 5. 授权状态机

```
发现群号 → 加入协作会话 → 请求提供执行 Agent
                              ↓ 群主批准
                         绑定项目范围
                              ↓
                    成为可调度蜂群成员
                              ↓
              移除 / 离群 / 踢出 / 授权失效
                              ↓
                    停止新调度并撤销访问
```

群组产生的 Agent 访问授权必须带来源标识 `swarm:<groupNumber>` 与项目范围。不得覆盖用户已单独创建的访问授权；撤销蜂群授权也不得误删独立授权。

## 6. 编排与运行

PM 先输出待确认任务图：节点包含目标、输入、验收标准、负责人、依赖、读写策略和预期产物。用户确认后才调度写入节点；只读研究节点可按策略自动开始。

调度器只会在全部依赖完成、成员在线、授权有效、工作区锁可获得时启动任务。每项任务有 `todo → assigned → running → done | blocked | error` 状态；失败必须携带原因，不能静默转交。成员完成后可提出后继任务，但新增写入任务仍受工作区锁和用户策略限制。

## 7. 强制迁移

应用启动时将所有旧协作组升级为 `swarm` 模式，保留 ID、名称、群号、成员、任务与历史：

- 旧项目成员迁移为绑定项目的蜂群成员，默认策略为 `read`；已有 PM 保持 PM 身份。
- 每个旧协作组自动生成 `v2` 蜂群策略，默认“需确认的写入”和“每工作区单写入者”。
- 旧任务原状态保留；没有明确写权限的历史任务不会自动重跑。
- 迁移幂等、可恢复，不提供旧 UI 模式回退；发生数据异常时保留原字段并显示迁移错误，不删除历史记录。

单项目不迁移为协作组，不改写其项目配置。

## 8. 分期交付

### 阶段 A：领域迁移与安全策略（当前）

- 强制把本地协作组规范为 `swarm`，保存版本和默认执行策略。
- 成员保存职责、Provider/模型快照和运行/写入策略；执行时仍以绑定项目的真实配置为准。
- 为工作区写锁、成员授权状态和迁移增加单元测试。

### 阶段 B：任务图与桌面工作台

- PM 生成可编辑任务图，桌面显示节点、依赖、成员、产物和运行状态。
- 新成员改为“请求加入 → 群主批准 → 选择项目范围”，不再把群号直接等同于执行权限。

### 阶段 C：跨账号成员与移动控制

- Relay 增加来源可追溯的蜂群执行授权与撤销。
- Android 显示任务图、待批准操作和产物摘要，支持人类介入。

### 阶段 D：隔离并行编码

- 管理 worktree/分支生命周期、合并审批、冲突回退和测试证据。
- 只有这一阶段完成后，才允许多个写入成员并行处理同一仓库。

## 9. 验收标准

- 旧协作组启动后全部显示为蜂群，历史、成员和群号完整保留。
- 同一项目目录上的第二个写入任务被拒绝或阻塞，绝不并发写入。
- 不同账号加入后只能看到已授权蜂群内容；未获批准的 Agent 不可接收执行任务。
- 移除成员后不再领取新任务，且仅撤销由蜂群创建的授权。
- 单项目会话、队列、引导、停止和移动端控制回归通过。
