# 协作组群聊设计

> 状态：已落地主流程。文件名保留用于兼容旧链接；产品不再把协作组定义为任务空间或 PM 编排系统。

## 1. 产品定义

协作组是一个 Agent 群聊。用户把不同设备、不同项目、不同账号或不同模型的 Agent 拉进同一个群，然后直接发消息指挥它们工作。

它只解决四件事：

1. 创建或加入一个群。
2. 选择本地和远程 Agent 作为成员。
3. 在一个共享消息流中发指令、看回复和错误。
4. 清楚看到成员是否在线、是否运行中、是否有执行权限。

单项目会话保持原样，不会被迁移为协作组，也不需要经过群聊才能使用。

## 2. 消息路由

用户消息遵循简单且可预测的规则：

| 输入 | 行为 |
| --- | --- |
| 普通消息 | 派发给群内所有已绑定且当前可用的 Agent。 |
| `@成员名` | 只派发给匹配成员。 |
| `@all` / `@全部` | 明确派发给所有可用成员。 |
| 未识别的 `@名称` | 不进行群发，显示路由失败，避免误操作。 |
| 没有可用成员 | 保留用户消息，并提示当前没有在线或已连接的成员。 |

Agent 回复仍进入同一个群消息流，并标记成员名、绑定项目、运行状态和错误。成员之间的自动交接不是默认交互；需要时只能通过显式 `@` 触发。

## 3. 成员模型

协作组成员是一个可执行 Agent 绑定，而不是角色或任务节点：

```text
账号 + Agent 设备 + 项目 + Provider + Model + 当前在线状态
```

一个群可以同时包含：

- 本机的多个项目 Agent
- 其他电脑上的远程 Agent
- 不同账号授权的 Agent
- 使用 Claude、Codex 或后续 Provider 的 Agent

群本身不统一覆盖成员的模型和密钥。每个成员继续使用其绑定项目的真实运行时配置。

## 4. 跨账号授权

群号只用于发现和加入群聊，不自动授予代码或文件执行权。

跨账号 Agent 的流程是：

```text
搜索群号 -> 加入群聊 -> 申请共享指定项目 -> 群主批准 -> 成为可执行成员
```

授权必须满足：

- 只包含申请时选择的项目范围。
- 不复制 API Key、CLI 登录态或本地文件到 Relay。
- 可以单独撤销，不影响用户已有的独立设备授权。
- Agent 离线时仍可显示在成员列表中，但不会被当作可用执行目标。

## 5. 数据边界

| 数据 | 保存位置 |
| --- | --- |
| 群定义、成员绑定、群消息和运行状态 | 群所属桌面端 |
| 群号、成员关系和跨账号执行申请 | Relay |
| 模型密钥、CLI 登录态、项目文件 | 各 Agent 所在设备 |
| Android 展示数据 | 从连接的桌面端实时同步 |

桌面端是群消息和成员状态的事实来源。Relay 负责连接、发现和授权元数据，不复制完整项目环境。

## 6. 界面范围

桌面端默认只展示：

- 群名称和可选群说明
- 本地/远程 Agent 选择器
- 群号发布与加入
- 跨账号执行申请和审批
- 群聊入口、成员状态和回复

Android 默认只展示：

- 协作组列表
- 群聊消息
- `@` 成员选择
- 成员在线、运行中和错误状态
- 跨账号执行授权操作

默认界面不再展示 PM Agent、目标规划、任务草案、任务图、验收、定时任务、角色专长或工作树合并。

## 7. 兼容策略

旧版本已经保存的任务、PM 和调度字段暂时保留在底层存储与协议中，避免升级后破坏历史数据或旧客户端。兼容层遵循以下规则：

- 启动和保存协作组时不再自动创建 PM Agent。
- 旧 PM 成员可以继续从存储读取，但不参与普通群聊广播。
- 旧任务 IPC 暂时保留，桌面和 Android 的默认入口不再暴露。
- 新功能不得继续依赖 PM、任务图或复杂角色模型。

## 8. 验收标准

- 新建协作组不会自动出现 PM Agent。
- 普通消息会发给所有在线且已绑定的成员。
- `@成员名` 只触发指定成员，未知 `@` 不会误群发。
- 本地和远程 Agent 可以同时存在于一个群中，并分别显示状态。
- 跨账号成员未获执行授权前不能访问对方项目。
- 原有单项目聊天、队列、引导和停止逻辑不受影响。
