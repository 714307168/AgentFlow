# 多端扩展计划

更新时间：2026-04-19

## 1. 背景

当前项目的稳定主链路已经是：

- Windows 桌面端 `local-agent`
- Android 客户端
- relay-server

这条链路已经具备：

- 项目级消息和活动同步
- 增量同步、缓存优先、revision / delta / after_seq
- 更新中心
- 项目级授权
- 图片和文件并入消息时间线

因此下一阶段不应继续停留在“修局部补丁”，而应开始把多端扩展计划收成明确路线。

## 2. 各端定位

### 2.1 Windows / macOS

定位：完整主控端。

职责：

- 持有本地 CLI 运行环境
- 负责项目执行、会话历史、文件源头
- 承担更完整的设置、诊断、发布和自动化能力

### 2.2 Android / iOS

定位：移动主客户端。

职责：

- 查看项目状态、聊天、活动、附件和文件
- 发消息、收结果、收通知
- 进行轻量控制、审批、日志上传和诊断

### 2.3 微信小程序 Lite

定位：轻量副客户端。

职责：

- 快速查看消息和状态
- 做轻量回复和提醒确认
- 接收文件

不承担：

- 完整实时控制
- 复杂设置
- 重型任务编排

## 3. 推荐顺序

建议顺序：

1. `mac`
2. 统一文件传输底座
3. `iOS Safe Track`
4. `微信小程序 Lite`

原因：

- `mac` 与现有 Electron 桌面端最接近，投入最小，收益最快。
- 文件传输是后续所有新端都会依赖的公共底座，应该先统一。
- `iOS` 有审核约束，必须先按“可上架能力”拆边界。
- 小程序更适合作为轻入口，不适合作为第一优先级主控制端。

## 4. 分阶段计划

### P0：mac 首发

目标：

- 补齐桌面双平台能力
- 进入统一更新中心

范围：

- `macOS` 构建产物
- `arm64 / universal` 策略
- 自动更新检查和安装链路
- 日志目录、数据目录、权限提示适配
- 标题栏、窗口唤起、文件打开行为适配

发版节点：

- `R-mac-first`

### P1：统一文件传输底座

目标：

- 让文件传输成为跨端统一能力，而不是每个端重复做一套

范围：

- relay-server 统一 transfer 域
- 文件元信息、上传、下载、回执
- 消息时间线中的 file message 继续复用
- capability layer 继续按端降级

发版节点：

- `R-cross-end-transfer`

### P2：iOS Safe Track

目标：

- 做“能过审、能接住消息和文件”的 iOS 首发能力

首期范围：

- 登录和设备绑定
- 项目消息列表
- 项目聊天
- 协作组聊天
- 状态查看
- 文件接收和下载
- 日志上传

明确不进首发：

- 完整桌面镜像式控制
- 重度后台常驻
- 与 Android 完全同节奏的所有实时控制行为

发版节点：

- `R-ios-safe-track`

### P3：微信小程序 Lite

目标：

- 做一个“快进来、快查看、快回复、快离开”的轻量入口

首期范围：

- 登录和设备识别
- 消息列表
- 项目聊天只读 + 快速回复
- 协作组消息查看 + `@PM`
- 最近任务状态
- 文件消息接收和下载
- 一键重连 / 一键刷新

发版节点：

- `R-mini-lite`

### P4：设置页结构重整

目标：

- 继续拆设置页，减少大文件和重复逻辑

建议一级分组：

1. 连接与账号
2. 项目与协作组
3. 消息与文件
4. 任务与自动化
5. 更新与日志
6. 高级设置

发版节点：

- `R-settings-restructure`

## 5. 跨端统一要求

无论新增哪个端，都必须继续遵守这几个约束：

1. 不打散现有 revision / delta / after_seq 的同步主线。
2. 优先使用本地缓存，再做增量拉取，不回到整包覆盖。
3. 项目级授权必须贯穿所有新端，不允许默认全项目可见。
4. capability layer 要继续统一，避免协议按客户端越分越多。
5. 文件传输继续留在消息时间线里，不再额外发明单独的“发文件功能页”。
6. 发版信息必须同步到更新中心和路线图节点。

## 6. 验收标准

### mac

- 可登录、连接、同步、聊天、协作、更新。
- 数据目录、日志、自动更新和权限路径清晰可用。

### iOS

- 能稳定接住消息、活动、附件和文件。
- 能在审核可接受边界内完成首发。

### 小程序

- 能快速查看、快速回复、快速接收文件。
- 不承担复杂长连接和重型控制。

### 统一文件传输

- 上传、下载、回执、失败重试完整闭环。
- 不破坏原有消息同步链路。

## 7. 风险与前置条件

主要风险：

- `iOS` 审核风险高，不能按安卓镜像思路直接推进。
- `mac` 涉及签名、notarization、自动更新和权限适配。
- 小程序的长连接和后台能力有限，必须坚持 Lite 定位。

前置条件：

- 继续保持 Windows + Android + relay-server 主链路稳定。
- 继续完善发布和更新中心一致性。
- 继续控制消息和文件同步流量，不因新端接入把协议重新做重。
