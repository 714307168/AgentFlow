# 受控授权远程协作设计

更新时间：2026-04-17

## 1. 背景

`AgentFlow` 现在已经具备了这类能力基础：

- 桌面端本地 Agent 持续连接 relay-server
- Android 端可以查看项目、聊天、活动、文件和运行状态
- 设备、项目、协作组、文件传输都已经进入同一套同步体系

但从真实使用场景看，后续很容易继续往“远程协作”方向走：

- 办公室电脑授权给自己下班后继续跟进
- 现场机器授权给同事远程排查或部署跟进
- 运维节点授权给值班同学看状态、收日志、收结果
- 某些项目只开放给特定账号，不希望一个账号默认看到全部项目

这里最容易走偏的点是：把它做成“谁拿到账号就能看整台机器、整套项目、所有附件”。

这一份文档的目标，就是明确一个更稳的方向：

- 它不是传统远程桌面授权
- 它更适合做“受控授权远程协作”
- 授权粒度尽量下沉到项目和能力，而不是只停留在账号级

## 2. 产品边界

### 2.1 它不是什么

- 不是开放整台电脑给别人直接操作
- 不是让被授权人自动拥有当前账号下全部项目
- 不是做复杂企业 IAM / RBAC 平台
- 不是一开始就做细到几十个开关的重权限后台

### 2.2 它是什么

- 让一台桌面设备成为“可被授权的远程协作节点”
- 让协作者围绕项目消息、运行状态、文件和结果进行协作
- 让授权范围默认收敛在“哪些项目 + 能做什么”
- 让被授权人不必直接接触完整桌面和本机原始环境

一句话说，就是：

> 授权的是“协作能力”，不是“整机控制权”。

## 3. 适用场景

### 3.1 现场调试

- 现场机器接入 `local-agent`
- 现场同学只负责接线、部署或观察
- 远端协作者被授权查看某几个项目的消息、状态和日志结果
- 需要时继续发跟进指令，不必开放整台桌面

### 3.2 部署跟进

- 发布机或构建机接入 relay
- 被授权人只看部署项目和部署结果
- 可以收文件、看日志、重试预设动作
- 不默认看到其他业务项目

### 3.3 远程办公

- 办公室电脑白天运行本地 CLI agent
- 下班或外出时，手机端继续接住消息和结果
- 若需要同事协作，也只授权某几个项目给指定账号

### 3.4 值班与排障

- 值班账号只看值班项目和异常项目
- 可以看最近活动、日志摘要、传输失败和连接状态
- 不自动拥有发布、删除、清缓存等高风险能力

## 4. 设计原则

1. 默认最小授权。先不给，再按项目和能力补。
2. 项目优先。授权首先回答“能看哪些项目”，其次才是“在项目里能做什么”。
3. 设备和项目分离。设备在线不等于设备上的所有项目都开放。
4. 能力包优先，不做一开始就极重的角色体系。
5. 高风险操作显式确认，且保留审计。
6. 授权要支持撤销、过期和临时授权，不做永久裸授权。

## 5. 建议授权模型

### 5.1 授权主体

首期只考虑两类主体：

- 账号
- 设备

账号是“谁”，设备是“从哪台端上来”。

建议授权判断同时参考这两层：

- 某账号是否被允许访问某台桌面节点
- 该账号当前登录的设备是否也在允许范围内

这样可以避免“账号一旦泄露，所有终端都直接拿到远程协作权”。

### 5.2 授权范围

建议把范围拆成三层：

1. 节点范围
   - 是否允许访问这台桌面节点
2. 项目范围
   - 全部项目
   - 指定项目
   - 指定项目组
3. 会话/协作范围
   - 是否可见协作组
   - 是否可收发文件
   - 是否可看诊断信息

其中最关键的是项目范围。

首期不要只做“授权账号 = 全项目可见”，而是支持：

- 授权账号时，同时勾选允许访问的项目
- 允许沿用当前账号登录体系，但单独裁切项目可见范围
- 后续新增项目默认不自动继承给外部协作者，除非显式勾选

这也是后续“项目级授权”应该真正落地的地方。

### 5.3 能力包

为了避免权限开关过碎，建议先提供 4 组能力包：

- `observe`
  - 看项目列表
  - 看聊天和活动
  - 看运行状态
  - 看文件消息元信息
- `collaborate`
  - 包含 `observe`
  - 发消息
  - @成员
  - 接收文件
  - 下载允许范围内的附件
- `operate`
  - 包含 `collaborate`
  - 触发预设动作
  - 重连、补拉、重试同步
  - 查看更多诊断摘要
- `admin`
  - 包含 `operate`
  - 管理授权
  - 发布版本
  - 删除高风险数据
  - 执行全局设置修改

这里的重点不是做复杂角色，而是给用户一个足够轻的选择入口。

### 5.4 高风险动作单独兜底

即使拿到了 `operate` 或 `admin`，以下能力仍建议单独确认：

- 删除项目
- 删除协作组
- 清理本地缓存
- 导出完整诊断包
- 发布版本到更新中心
- 下载敏感附件
- 执行会影响整机环境的动作

也就是说：

- 常规协作走能力包
- 高风险动作走二次确认和审计

## 6. 建议交互

### 6.1 授权入口

建议把授权入口统一放在“连接与账号 / 项目与协作组”之间，不再散在多个弹窗里。

授权动作建议长这样：

1. 选择要授权的账号
2. 选择允许访问的桌面节点或设备
3. 勾选允许访问的项目
4. 选择能力包：`observe / collaborate / operate / admin`
5. 可选设置过期时间、备注、临时授权原因

### 6.2 首期 UI 原则

首期不要引入很重的角色编辑器，只做：

- 账号选择
- 项目多选
- 能力包单选
- 过期时间
- 撤销授权

这样能先把最核心的“项目级授权”落地。

### 6.3 文案方向

产品文案应统一强调：

- 这是受控授权远程协作
- 不是远程桌面接管
- 不是账号授权后自动拥有全部项目

## 7. 数据模型建议

首期可以先补一张轻量授权表，不要一次做太重。

建议新增：

- `node_access_grants`

核心字段建议：

- `grant_id`
- `owner_account_id`
- `target_account_id`
- `target_device_id` 可空
- `desktop_device_id`
- `scope_type`
- `scope_project_ids`
- `capability_bundle`
- `allow_file_download`
- `allow_diagnostics`
- `expires_at`
- `created_at`
- `revoked_at`
- `note`

如果后面要继续做审计，再补：

- `node_access_audit_logs`

## 8. API 与同步建议

首期建议新增轻量授权域，不要把逻辑散在项目接口里：

- `GET /api/access/grants`
- `POST /api/access/grants`
- `PATCH /api/access/grants/:id`
- `POST /api/access/grants/:id/revoke`
- `GET /api/access/effective-scope`

客户端每次拿项目列表或会话摘要前，可以先拿一份当前有效 scope：

- 当前账号能看哪些节点
- 当前账号能看哪些项目
- 当前账号当前设备是否受限
- 当前是否允许文件下载 / 诊断导出 / 预设动作

这样后续桌面端、Android、iOS、小程序都能走同一套授权口径。

## 9. 与现有 roadmap 的关系

这份设计会直接影响这些已规划项：

- `7.6 权限模型`
- 文件传输权限边界
- 小程序敏感附件下载控制
- iOS / 小程序 / mac 多端能力裁切
- 后续协作组和项目级授权收口

所以后续实现顺序建议是：

1. 先补授权模型和 scope 查询
2. 再把项目列表和会话入口按 scope 裁切
3. 再把文件下载、诊断导出、预设动作挂到 capability bundle

## 11. 当前结论

后续“远程授权”最稳的做法，不是把它做成更重的远程桌面，也不是只做账号级开关。

更合适的路线是：

1. 把桌面节点视为可被授权的协作入口
2. 授权时同时裁切项目范围
3. 用轻量能力包控制“能看什么、能发什么、能操作什么”
4. 对高风险动作保留单独确认和审计

这样既能覆盖现场调试、部署跟进、远程办公，也不会把整个系统推向一个过重的权限平台。
