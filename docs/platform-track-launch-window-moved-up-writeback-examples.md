# 平台专项首发窗口临时前移后的短回写示例

更新时间：2026-04-22

这份文档不再讲完整模板，而是直接给出“平台专项原本按既定首发窗口推进，但因为业务节奏、审核机会、联动发布或上游排期变化，首发窗口被临时前移时，路线图里该怎么短回写”的样例。它适合解决这几个问题：

- 平台专项并不是延期，而是首发节奏被整体提前，但路线图里缺少“窗口前移”的短语气
- 已经有首发延期、错过窗口和重新进入首发准备样例，但缺少“要更早收口”的表达方式
- 想把 mac / iOS / 小程序 这类平台节点在窗口突然前移后的压缩范围、保留边界和提前动作控制在摘要级别

## 1. 使用方式

推荐顺序：
1. 先在平台专项文档、发版计划或验收清单里写清楚原定窗口、为什么临时前移、前移后还保留哪些边界。
2. 再从完整内容里抽 2 到 4 行回写到路线图。
3. 路线图里只保留“窗口为什么提前、当前压缩到什么范围、首发前必须优先收什么、何时做最终确认”，不要把所有排期协同细节原样搬进去。

路线图里最好让人一眼看出：

- 这不是常规推进，而是首发窗口被临时提前
- 当前是主动收敛范围还是只是压缩验证节奏
- 哪些动作必须前置，哪些范围继续冻结
- 后面是直接进入发版判断，还是先做提前验收

## 2. 因业务窗口前移而提前收口

### 2.1 mac

~~~text
- R-mac-first 当前首发窗口临时前移：
  - 受桌面端现场部署节奏影响，首发判断提前到本周内完成，安装、更新和回退链路需要先行收口
  - 当前继续只保留最小可发布主链路，不并回更大桌面体验优化范围
  - 下一步先补齐提前验收和回归结果，再决定是否按前移窗口首发
~~~

### 2.2 iOS Safe Track

~~~text
- R-ios-safe-track 当前首发窗口临时前移：
  - Safe Track 因远程办公场景联动需求，首发判断提前，登录、项目列表和消息查看链路优先收口
  - 当前继续维持窄边界，不顺带扩到完整远控能力
  - 下一步先完成前移窗口前的主链路核查，再决定是否进入正式首发
~~~

## 3. 因审核机会前移而提前准备

### 3.1 iOS Safe Track

~~~text
- R-ios-safe-track 当前首发窗口临时前移：
  - 审核和上架机会较原计划提前，当前需要把已确认范围压到可快速验收状态
  - Safe Track 继续只保留轻量可用能力，不新增任何边界
  - 下一步先完成提前审核前的核查，再决定是否锁定这轮窗口
~~~

### 3.2 小程序 Lite

~~~text
- R-mini-lite 当前首发窗口临时前移：
  - 轻入口联动发布节奏前移，Lite 需要提前把查看、快回和状态确认主链路收稳
  - 当前不补重交互和更大产品扩展，只维持 Lite 定位
  - 下一步先补齐前移窗口前的轻量验收，再决定是否跟随首发
~~~

## 4. 因联动排期变化而压缩范围

### 4.1 mac

~~~text
- R-mac-first 当前首发窗口临时前移：
  - 联动排期较原计划提前，当前不再按原宽范围推进，先只围绕安装、更新和回退链路压缩收口
  - 桌面侧扩展体验和附加自动化能力继续延后，不并入本轮前移窗口
  - 下一步先完成压缩范围内回归，再决定是否锁定前移后的首发安排
~~~

### 4.2 小程序 Lite

~~~text
- R-mini-lite 当前首发窗口临时前移：
  - 配套联动节奏突然提前，当前只保留 Lite 最小可用链路，避免窗口前移后范围失控
  - 当前继续冻结额外入口和复杂交互，不借机扩边界
  - 下一步先确认联动条件和轻量验收结果，再决定是否进入首发判断
~~~

## 5. 窗口前移但保持窄边界

### 5.1 iOS Safe Track

~~~text
- R-ios-safe-track 当前首发窗口临时前移：
  - 虽然首发节奏提前，但当前只恢复 Safe Track 范围内的首发准备，不扩大产品边界
  - 延后范围继续冻结，不因窗口前移而临时加项
  - 下一步先按前移窗口做最小闭环验证，再决定是否正式首发
~~~

### 5.2 mac

~~~text
- R-mac-first 当前首发窗口临时前移：
  - 当前只是把最小发布链路的判断时间前提，不代表桌面端整体能力一并提前
  - 扩展体验优化继续延后，避免窗口前移带来范围膨胀
  - 下一步先看前移窗口前的验收结论，再决定是否首发
~~~

## 6. 不推荐写法

不要在路线图里继续写这种又长又模糊的段落：

~~~text
这个平台原本是按后面的窗口发，不过现在看起来可能要提前一点，所以相关内容最近都会往前赶一赶，具体哪些功能真的要跟着提前、哪些还是保留、会不会因为太赶再改计划，后面再统一看。
~~~

原因：
- 看不出是不是明确进入“窗口前移”状态
- 看不出当前压缩后的边界是什么
- 看不出哪些动作必须前置完成
- 看不出后面是提前首发还是继续观察

## 7. 当前结论

后续平台专项如果不是简单延期，而是原定首发窗口被临时前移，优先复用这份文档里的短样例，把前移原因、压缩边界和前置动作压成路线图语气，避免总览继续膨胀。
