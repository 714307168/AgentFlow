# iOS Safe Track 规划

更新时间：2026-04-19

这份文档用于定义 `R-ios-safe-track` 的首发边界。目标不是先做一个“安卓镜像版 iOS”，而是先定义一套能上线、能维护、能接住消息和文件的 iOS companion 方案。

## 1. 目标

iOS 首发优先解决这几件事：

- 能登录并绑定当前账号
- 能查看项目列表、聊天、活动和运行状态
- 能接收消息里的图片与文件
- 能做轻量回复与操作
- 能在审核可接受边界内落地

不把首发目标定成：

- 完整实时远程控制
- 与 Android 完全同构
- 长时间后台保活的重控制终端

## 2. 产品定位

iOS 的定位是“移动 companion 主客户端”，但不是“桌面能力完整映射”。

它应该承担：

- 消息查看与回复
- 协作组查看与 @ 交互
- 项目状态与运行结果查看
- 附件和文件接收
- 日志上传与问题反馈

它不应该在首发承担：

- 完整桌面镜像式控制
- 对本地 CLI 运行环境的深控制
- 复杂后台恢复和超长时常驻连接

## 3. 首发能力边界

### 3.1 必做

- 登录
- 账号与设备绑定
- 项目列表
- 项目聊天
- 协作组聊天
- 运行状态查看
- 消息内图片 / 文件接收与下载
- 日志上传
- 版本检查

### 3.2 可选但不阻塞首发

- 推送通知
- 轻量文件预览
- 本地消息搜索
- 只读诊断摘要

### 3.3 不进首发

- 完整远程桌面式控制
- 强实时多会话复杂调度
- Android 等级的后台恢复链路
- 首发就引入新的专属协议分支

## 4. API 与协议边界

iOS 首发原则：

1. 尽量复用现有 relay-server 公共接口。
2. 尽量复用 Android 已有的消息、同步、更新、附件协议。
3. 不为了 iOS 首发单独分叉出一套新消息模型。
4. 必须继续遵守项目级授权边界。

### 4.1 应复用的能力

- 项目列表 / 目录 revision
- 消息增量同步
- `after_seq`
- `snapshot_revision`
- `revision / meta / delta`
- 图片与文件消息时间线
- 更新检查接口
- 项目级授权 `effective-scope`

### 4.2 不建议首发新增的能力

- iOS 专属会话协议
- iOS 专属文件传输协议
- iOS 专属权限模型

## 5. 本地缓存策略

iOS 首发建议继续沿用当前移动端策略：

- 项目列表本地缓存
- 最近消息窗口本地缓存
- 会话快照缓存
- 当前账号、更新设置、基础偏好缓存

但要控制边界：

- 不把完整大历史长期常驻到本地
- 不把冷项目做成高频全量回写
- 不因为 iOS 新端接入就把现有增量同步打回整包覆盖

## 6. 文件与附件边界

iOS 首发继续沿用“文件并入消息时间线”的方向。

要求：

- 图片和文件作为消息附件展示
- 用户从消息里直接下载
- 首发不单独做一个复杂的发文件中心
- 后续统一传输底座上线后再扩大发送能力

## 7. 审核风险控制

iOS 风险重点不在“能不能做出来”，而在“按什么边界提交”。

首发必须控制：

- 不强调远程桌面或桌面镜像
- 不把客户端描述成通用 thin client
- 不把复杂后台远程控制作为核心卖点
- 界面和文案聚焦项目消息、协作、文件和状态

## 8. 首发验收清单

至少要验证：

- 登录和账号绑定
- 项目列表同步
- 聊天消息增量刷新
- 协作组聊天展示
- 图片 / 文件接收与下载
- 项目级授权限制生效
- 更新检查
- 日志上传

## 10. 当前结论

iOS 首发不应该追求“功能最多”，而应该先把“消息、状态、文件、授权边界”四件事做稳，并保持协议和发布链路与现有 Android / desktop 主线一致。
