# 冷项目同步与项目签名验收清单

更新时间：2026-04-19

这份文档用于把 `project_signature + sync_bucket + TTL` 这套省流量机制，整理成一份更容易执行的验收入口。

它和 [Project Sync Signature 设计](./project-sync-signature-design.md) 的关系是：

- 原设计文档解释为什么要这样做
- 这份文档负责说明怎么验收有没有真的做到省流量

## 1. 验收目标

确认下面这几件事已经成立：

1. 冷项目和休眠项目不会每轮都参与同步
2. 活跃项目仍然能及时看到变化
3. 项目级签名只表示“项目壳变化”，不是拿来替代正文校验
4. App 回前台、自动恢复、列表刷新时，请求体和响应体都明显收敛

## 2. 关键概念

### `project_signature`

只表示项目会话壳是否变化，例如：

- 最新消息序列
- 最近活动时间
- 当前运行状态
- 队列数量
- 当前对话

不应该直接包含：

- 完整消息正文
- 大附件明细
- 全量活动列表

### `sync_bucket`

推荐至少保留四档：

- `hot`
- `warm`
- `cold`
- `dormant`

### TTL

推荐目标：

- `hot`：正常高频参与
- `warm`：恢复时参与，但频率低于 `hot`
- `cold`：只在 TTL 到期后抽样检查
- `dormant`：默认跳过，显式打开再激活

## 3. 重点场景

### 3.1 App 启动

预期：

- 先看设备级 revision 是否变化
- 未变化时不应把所有冷项目再拉一遍
- 活跃项目仍然能尽快补齐

### 3.2 App 回前台

预期：

- 热项目立即参与同步
- 冷项目不因一次回前台就全部重刷
- 休眠项目默认不进入请求体

### 3.3 打开某个冷项目

预期：

- 该项目立刻提升为 `hot`
- 先本地缓存渲染
- 再只同步这个项目的最新增量

### 3.4 项目刚产生新消息或任务状态变化

预期：

- local-agent 立即刷新该项目签名
- 该项目进入 changed-project set
- 该项目热度提升，客户端能及时看到

## 4. 请求与响应验收

### 请求侧

- [ ] Android 常规恢复请求不再携带所有项目的签名
- [ ] 活跃项目签名集合明显少于总项目数
- [ ] `cold / dormant` 项目默认不进入每轮请求体

### 响应侧

- [ ] 服务端优先返回 changed-project set 或等价结果
- [ ] 未变化的冷项目不会重复返回完整会话壳
- [ ] 响应体大小随着冷项目数量增加不应线性膨胀

## 5. 本地存储验收

- [ ] Android 本地持久化 `project_signature`
- [ ] Android 本地持久化 `sync_bucket`
- [ ] Android 本地持久化 `next_background_check_after` 或等价 TTL 字段
- [ ] 项目壳未变化时，不会反复重写本地会话缓存

## 6. 体验验收

- [ ] 用户回到前台时，常用项目仍然很快可见
- [ ] 长时间没打开的项目不会拖慢消息页恢复
- [ ] 打开冷项目时，仍然能先看到本地缓存，再补最新状态
- [ ] 不会出现“冷项目虽然不常用，但一旦有新变化却长期看不到”的假省流量

## 7. 建议指标

至少建议对比这几项：

- 单次前台恢复请求体字节数
- 单次前台恢复响应体字节数
- 参与本轮同步的项目数
- 被跳过的 `cold / dormant` 项目数
- 打开冷项目后的首次可见耗时

建议记录模板：

~~~text
scenario:
total projects:
hot projects:
warm projects:
cold projects:
dormant projects:
request bytes:
response bytes:
visible latency:
notes:
~~~

## 8. 常见失效信号

出现下面这些现象，说明这套设计还没真正落地：

- 项目再多，请求体仍然几乎线性增长
- 只要回前台，所有项目都会重刷一次
- 冷项目虽然长期没变化，但本地缓存仍被频繁重写
- 打开冷项目时，不是先用缓存，而是整个页面等远端

## 10. 当前结论

这套机制的关键不是“每次都给所有项目算 md5”，而是“只让值得同步的项目进入同步窗口”。验收时也必须围绕这个目标看请求体、响应体和本地事务是否真的变少。
